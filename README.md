# CarRental

Backend for the car rental system at an airport, done for the technical challenge.

## Running it

You only need the .NET 10 SDK. The SQLite database (`carrental.db`) is created by the API the first time it starts, so there's nothing to set up.

## The API

You register and log in to get a JWT. There are two roles: a **customer** can check availability, book a car and cancel their own bookings until they start, and an **employee** can do everything else (cars, customers, rentals, booking for any customer). Errors always come back as problem details JSON.

The full list of endpoints with examples is in [docs/API.md](docs/API.md), and there's an OpenAPI file in [docs/openapi.json](docs/openapi.json) in case it's useful to generate the Angular client.

## How it's organized

Four projects plus tests:

- `CarRental.Domain`: entities, enums, domain exceptions and the repository interfaces.
- `CarRental.Application`: the use cases as CQRS commands and queries with MediatR, validation with FluentValidation, and the pipeline behaviors (validation, cache, cache invalidation).
- `CarRental.Infrastructure`: EF Core with SQLite, repositories, JWT, password hashing and the in-memory cache.
- `CarRental.API`: controllers, the global exception handler and the startup.

Other things worth knowing: Repository and Unit of Work for data access, soft delete for cars and customers, and an in-memory cache for reads that gets cleared when something changes.

## Assumptions and simplifications

Things I decided to leave simple to keep the challenge manageable:

- **Anyone can register as an employee.** `POST /api/auth/register` accepts both roles. In a real system employee accounts wouldn't be self service, an admin would create or invite them.
- **Customers created by an employee have no login.** `POST /api/customers` (used for example for someone at the counter) only creates the customer profile. A customer who registers by themselves gets a user and a profile together. Ideally, when an employee creates a customer the system should generate a password and send them an email to activate their user.
- **The database isn't persistent in Docker.** There's no volume, so the SQLite file lives inside the container and is lost when the container is removed.
- **No migrations.** The database is created with `EnsureCreated()` when the API starts, which is what makes it work without any setup. If the model changes, the `.db` file has to be deleted.
- **The JWT secret is in `appsettings.json`**, so the project runs right after cloning. It should come from an environment variable or a secret store in a real deployment.
- **The Docker image runs in Development mode** so Swagger is available, and it only listens on HTTP. HTTPS would be handled by a proxy in front.
- **Cars and customers with rentals can't be deleted.** Otherwise they're soft deleted.
- **The cache lives in memory**, so it only works properly with one instance of the API. With several you'd need something shared like Redis.
- **The customer id is an integer** generated by the database, not a string like in the class diagram.
- The `Service` entity from the diagram is modeled but there are no endpoints for it, since the challenge doesn't ask for anything about services.
- **CORS only allows `http://localhost:4200`**, the default port of the Angular dev server. Other origins go in `Cors:AllowedOrigins` in `appsettings.json` (or the `Cors__AllowedOrigins__0` environment variable).
- Not done: pagination on the lists, refresh tokens and password rules beyond a minimum length.

## How I used AI

I used Claude (Claude Code with the Sonnet 5 model) during the whole challenge. The main reason is that I had used CQRS a long time ago and I didn't remember it well, so I mostly used it to figure out how to structure the project (which layers, where each piece goes, how MediatR fits with validation and so on) and to get suggestions that I could accept or throw away.

My workflow was to say what I wanted next, for example "add authentication", and ask for its opinion first. For the bigger things it proposed a plan or a couple of options and I chose one before any code was written. After that it also wrote the code we had agreed on, in the repo, and I went through the changes and asked for corrections when something wasn't what I wanted.

Some examples of how that went:

- **Accepted**: MediatR with FluentValidation in the pipeline for the CQRS part, a small JWT setup of our own instead of the full ASP.NET Identity, and soft delete through a global query filter in EF Core.
- **Changed**: the first version had entities with factory methods and validation inside. I wanted plain entities, so the validation moved to the validators and the handlers. It also suggested a shared helper for soft delete that I asked to remove, keeping the two repositories explicit (but keeping the generic query filter). I also noticed by myself that users weren't linked to customers, which meant a customer could book for anybody, and we fixed it linking the user to its customer profile.
- **Rejected**: for customers created by an employee it listed three options (link a user right away, remove those endpoints, or leave it and document it). I picked the last one. I also decided against adding a Docker volume.

I didn't set up custom agents, skills or MCP servers. The repo has a `CLAUDE.md` with notes about the project so the assistant keeps the same conventions between sessions.
